# Site Chrome — Test Case Inventory

Companion to [search-test-inventory.md](search-test-inventory.md), same method and column
meanings (see that doc's Purpose section) - built from a read of the actual implementation
to find where behavior branches, with the **Expected** column stating what should happen
rather than what the code happens to do. Covers the elements that render on (almost) every
page, rather than the search results page itself: the first-visit modal, cookie consent, the
navbar, and the footer. The one banner in the app (`LocationBasedAlertBanner`) only renders
on the search results page, so its test cases live in section 14 of
[search-test-inventory.md](search-test-inventory.md), not here.

## 2. Analytics/Cookie Consent (`react-hook-consent`)

Site-wide (every route), not homepage-only. Persisted to `localStorage['react-hook-consent']`
(not a cookie, despite the "cookie consent" name), keyed by a hash of the app's consent
config - if that config changes, previously-stored consent is treated as stale and the
banner reappears.

**Known dead code, not a coverage gap:** `providers/index.tsx` defines `window.reopenConsent`
(intended to let something re-trigger the banner) but nothing in the app calls it - no
footer/settings link exists to reopen consent that way. `onAccept`/`onDeny` callbacks defined
on the `ga4` service config are also never invoked by the consent library (not part of its
config type). Don't write tests asserting either does something; if "let a user reopen
consent settings from the footer" is a real intended feature, that's a feature gap to build,
not a test to write against current behavior.

## Known Non-Goals / Dead Code

- **No functional "decline" path on the anti-hate modal** (§1.5) - both Accept and the close-X
  set the same acceptance cookie. Don't write a test asserting a decline path exists until a
  product decision confirms one should.
- **`window.reopenConsent`** and the `ga4` service's `onAccept`/`onDeny` callbacks (§2) are
  dead code with no callers - don't test them as if they're reachable features.
- **Footer logo has no `/` link wrapper**, asymmetric with the navbar logo (§4.10) - flagged,
  not assumed to be either correct or a bug.
