# Search Feature — API/Router Test Case Inventory

## Purpose

Companion to [search-test-inventory.md](search-test-inventory.md) and
[site-chrome-test-inventory.md](site-chrome-test-inventory.md), same method and column meanings
(see that doc's Purpose section). Those two docs cover the public-facing UI, which the earlier
effort confirmed is now fully worked through. This doc covers the layer underneath it: the
tRPC routers/procedures those UI components actually call over the wire, and the raw-SQL/
external-API code those procedures call in turn.

**Starting state (confirmed by direct investigation, not assumed):** every procedure listed
below currently has **zero** test coverage. The only existing tests anywhere in
`packages/api` cover `orgPhone` CRUD, one edit-mode-bar schema, and three admin `organization`
procedures unrelated to search. `packages/db` has no test runner at all. This is greenfield
coverage work, though not greenfield tooling - `packages/api/vitest.config.mts` already has a
working Vitest setup, and the existing tests establish a working
`vi.mock('@weareinreach/db', () => ({ prisma: { <model>: { <method>: vi.fn() } } }))` pattern to
extend.

**A real constraint specific to this layer, not present in the UI docs:** the core search query
(`organization.searchDistance`, all versions) is a single large `prisma.$queryRaw` call - the
actual matching/ranking/tie-breaking logic lives inside the raw SQL string itself, running
against PostGIS geo functions (`ST_DWithin`, `ST_Transform`, `ST_CoveredBy`, etc.). Mocking
`prisma.$queryRaw` to return a canned array tests everything _around_ that query (input
validation, result shaping, pagination math) but cannot verify the query's own matching/ranking
behavior is correct - that needs the SQL to actually execute against a real Postgres+PostGIS
instance.

**That instance already exists and is easy to use** - `docker/docker-compose.yml` runs a real
`postgis/postgis:15-3.4` container locally (confirmed running via `docker ps`), and `.env`'s
`DATABASE_URL` already points `packages/db`'s Prisma client at it
(`postgres://user:password@localhost:5432/inreach`, the same DB `pnpm dev` uses). No test
container needs to be stood up - cases below marked **Vitest (real local DB)** can run against it
directly, today. Two things worth being deliberate about, not blockers:

- **It's the shared local dev DB, not a throwaway one.** `searchDistance` itself is read-only, so
  testing it there is harmless. The §7 `savedList` mutations (create/delete list, `saveItem`)
  actually write rows - those need either a transaction rolled back at the end of each test, or
  explicit insert-then-delete fixtures, so test runs don't leave junk data behind.
- **Geo-matching assertions need known fixture rows, not whatever's currently synced into local
  data.** "Org X appears within 50mi of coordinate Y" is fragile if it depends on the DB's current
  real content, which can change on the next data sync. The reliable pattern is: insert one or two
  known `Organization`/`OrgLocation` rows at controlled coordinates in a `beforeEach`, run the
  query, assert, delete them in `afterEach` - same idea as the fixture pattern already used for the
  mocked-Prisma tests, just against real rows instead of a mock.
- **CI doesn't run any of this today, DB-backed or not** - `.github/workflows/test.yml`'s only job
  is `packages/ui`'s Vitest suite; even the 11 existing _mocked_ `packages/api` tests never run in
  CI. That's a separate, pre-existing gap (not something this doc's test cases create) - these
  tests are real and runnable locally against Docker right now, and extending CI to spin up the
  same `docker-compose.yml` services is a follow-on decision, not a prerequisite to writing them.

Cases below are marked **Vitest (shape only)** where mocking `prisma`/`$queryRaw` is sufficient,
and **Vitest (real local DB)** where the case needs the real query executing against real rows.

Same failing-test discipline as the other two docs: when a new test correctly fails against real
behavior, file it as a GitHub issue, keep the test red, reference the issue number in Status.

**Columns:** same as the other two docs - **Layer** (Vitest / Vitest (shape only) / Vitest (real
local DB) / Manual), **Status** (`Not started` / `Partial` / `Covered`, with a pointer to the test
file once one exists).

legacy schemas (V1 has no `version` field at all) still reachable via the same procedure.

## 5. Alerts (`organization.getAlerts`, `location.getAlerts`, `component.LocationBasedAlertBanner`)

**Corrected framing, found while writing these tests, not assumed**: this section originally
described `organization.getAlerts`/`location.getAlerts` as backing the already-UI-tested
Location-Based Alert Banner (§14 of the UI doc). That's wrong - grep confirms the banner
component (`packages/ui/components/core/LocationBasedAlertBanner/index.tsx`) calls
`api.component.LocationBasedAlertBanner.useQuery(...)`, a separate procedure

(`apps/app/src/pages/org/[slug]/[orgLocationId]/edit.tsx` and `index.tsx`), not public search.

## 7. Save/Favorites (`savedList.*`, `organization.isSaved`)
